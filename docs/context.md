## 고친 것
1. **작업 폴더**
   - 기본 작업 폴더를 허브 저장소 밖 `F:/01_프로젝트/90_개발/oddin-workspace`로 옮겼다(공유 메모리 별칭으로 예전 workspace 메모리를 이어받음).
   - 기본 작업 폴더 세션이면 플래너가 계획 JSON의 `workdir`에 실제 프로젝트 루트를 적는다. 후보는 `lib/projects.mjs`의 `knownProjects`(메모리 대응표·별칭·세션 폴더)와 요청·이전 대화·결정 노트·메모리에 적힌 경로.
   - `validWorkdir`로 검사(있는 폴더, 드라이브 루트·홈·시스템·허브 기록 폴더 아님)한 뒤 `jobs.applyWorkdir`가 `job.cwd`를 바꾸고, 체크포인트를 새 폴더 기준으로 다시 시작하고, 세션 `workdir`에 기억해 다음 요청이 거기서 시작한다(`jobs.startDir`).
   - 사용자가 직접 고른 폴더 세션·worktree 세션은 옮기지 않는다. 끄기 `config.workdir.auto:false`.
2. **지시문 다이어트**
   - 전역 메모리 목록은 두 CLI 지침(Claude `CLAUDE.md` import, Codex `AGENTS.md` AUTO 블록)에 이미 있어 허브 지시문에서는 뺀다(`memory-context.cjs`의 `skipGlobalIndex`; 다시 넣기 `config.context.globalIndex:true`).
   - 메모리 한도(글자): 플래너 1만·본문 5개, 배정 5천, 작업자 8천·4개, 보고 5천(`MEMORY_LIMITS`, `config.context.memory.<단계>`).
   - 세션 맥락: 결정 노트(잘리지 않음) + 최근 명령. 플래너 1만 2천 자·최근 4건, 작업자 8천 자·최근 2건, 건당 3천 자(`planHistory`·`workerHistory`).
   - 실측: 작업자 지시문 4만 5천 자 → 8,882자, 계획 지시문 → 1만 1,925자.
3. **추론 강도**
   - 작업마다 `settings.pace`: `quality`(기본) / `speed`. 화면은 입력창 아래 분배 방식 메뉴의 "작업 방식".
   - 품질 우선이면 자동 강도를 평소 단독 설정까지 올린다(`router.raiseToStandalone` — Codex `config.toml`의 `model_reasoning_effort`, 모델이 지원하지 않으면 지원하는 최고값). 한도 90% 이상인 쪽은 올리지 않는다. Claude는 평소 강도 설정이 따로 없어 그대로.
   - 속도 우선이면 예전처럼 근거 없는 xhigh 를 high 로 낮춘다.
   - 계획·배정·보고·기억 정리 같은 내부 단계는 그대로 high.
4. **대화 이어 쓰기**
   - 같은 세션 후속 요청에서, 직전 완료 요청의 같은 AI·같은 폴더 마지막 완료 작업의 CLI 대화를 이어 쓴다(`jobs.continuation` → `task.resumeSessionId`, `task.continuedFrom`). 한 요청에서 AI마다 한 작업만, 24시간 지난 대화·다른 폴더·갈래 원본은 새로 시작.
   - 이어 쓰는 작업자 지시문은 "[이어서]" 안내 + 결정 노트만(이전 명령은 그 대화에 이미 있음).
   - 이어 쓰기가 실패하면 새 대화로 한 번 다시(`task.continueFailed`). 끄기 `config.continuity.resume:false`, 기간 `config.continuity.maxAgeHours`.
5. **쪼개기 줄이기**
   - 플래너 규칙: 기본은 작업 1개(한 AI가 조사·기획·구현·검증까지). 나누는 것은 독립된 큰 결과물이 둘 이상이라 병렬 이득이 클 때·사용자가 비교를 원할 때만. 같은 결과물의 단계 분리 금지, 최대 4개.
   - 각 과제는 사용자 요청 원문을 먼저 그대로 인용하고 필요한 맥락만 덧붙인다. 말하지 않은 요구사항을 지어내지 않는다.
   - 분배 비율은 담당을 고르는 참고일 뿐, 비율을 맞추려고 쪼개지 않는다.
   - 디자인 기획 분리(`enforceDesignRule`, 사용자 규칙)는 그대로다.

## 눈으로 보는 결과물 (2026-10-04 추가)
사용자 규칙 "눈으로 보는건 무조건 아스트라가 하자" → 범위를 물었을 때 "전부 Astra". `config.designRule.mode:"whole"`.
- UI·화면·디자인·이미지·영상·애니메이션·3D·렌더 등은 Codex·gpt-6-astra 한 작업자가 기획부터 구현·눈 확인까지(나누지 않음 — 위 5번과 같은 이유).
- 예전 "기획(Fable)·구현(Sol)" 분리는 `mode:"split"`으로 되돌릴 수 있다.
- 같은 날 사용자가 "디자인은 페이블 / 눈으로 확인은 아스트라"로 바꿈 → 지금 설정은 `mode:"split"` + `check`: 디자인 기획(Fable, 한도 75%↑면 Astra) → 구현(Sol) → 눈으로 확인(Astra, 허브가 자동으로 붙임, 어긋난 곳은 고침). `whole` 모드는 남겨 둠.
